# autots

**Generate a `.neoc` interop header for an entire TypeScript surface, so neoc can use the TS/JS ecosystem.** Point it at a `tsconfig.json` (or entry `.ts`/`.d.ts` files); it walks **everything in scope** with [ts-morph](https://ts-morph.com) and — modelled on [cxx](https://cxx.rs)/autocxx — generates **safe nominal wrappers** (real neoc `struct`s over an opaque foreign handle) plus the raw `extern` imports, rather than exposing the naked foreign value.

autots is **convention-driven** and **project-aware** — no per-run flags. It reads an `[autots]` table from your project's `neoc.toml`, resolves each configured types package, and writes a single file — `src/main/neoc/autots/types.neoc` — holding every configured module's `extern` surface plus the ambient global surface.

## Why

neoc's only seam to a host is the `extern` declaration: every callable the host exposes is declared in `.neoc` so the compiler can type-check it. neoc's JS backend emits ES modules (`use` → `import`), so to use a TypeScript library from neoc you need a header describing its surface in neoc types. Writing that by hand for a real dependency is infeasible — this tool derives it from the TypeScript types you already have.

## Usage

Configure the modules you want in `neoc.toml`:

```toml
[autots]
modules = [
  { module = "bun:sqlite", types = "@types/bun" },
]
```

- `module` — the JS import specifier (the ambient `declare module "<module>"` to extract).
- `types` — the npm package providing the declarations. Its `.d.ts` entry is resolved from the nearest `node_modules` (walking up from the project root), honoring the package's `package.json` `types`/`typings` field, defaulting to `index.d.ts`.

Then run, from anywhere inside the project:

```sh
bun autots
```

It discovers `neoc.toml` (walking up from the working directory) and writes one file:

- `src/main/neoc/autots/types.neoc` — every configured `module`'s `extern` surface (one `#[extern(path = "<specifier>")] mod` block each, in config order), followed by the ambient global surface (`#[extern(ambient)]` items like `console`, `fetch`, the global `Bun`). Consumers `use autots::types::Database;`.

With no `neoc.toml` above the working directory, autots exits with an error.

Output (`src/main/neoc/autots/types.neoc`):

```neoc
// @generated by autots — do not edit.
extern {
    #[extern(path = "bun:sqlite")]
    mod sqlite {
        pub struct Changes { changes: number, lastInsertRowid: Unknown }
        pub struct Database { inTransaction: bool, filename: string, handle: number }
        impl Database {
            #[extern(constructor)] pub fn new(filename: string);
            pub fn run(self, sql: string) -> Changes;
            pub fn query(self, sql: string) -> Statement;
            // …
        }
    }
    // … one mod per configured module, then the ambient globals:
    #[extern(ambient, path = "console")]
    mod console { pub fn log(); pub fn error(); /* … */ }
}
```

The neoc value of an extern type **is** the target value — no wrapper, no `JsRef` indirection. A `use autots::types::Database;` in a consumer reconstructs the native `import … from "bun:sqlite"` from the `#[extern(path)]` metadata. See [`lang/EXTERN.md`](../../lang/EXTERN.md) for the model and the degradation policy (`Unknown`, dropped optionals, etc.).

## How it works

Rather than expose the raw foreign value, autots generates a **safe wrapper** that confines the dynamic access — the cxx/autocxx pattern:

- **A runtime-shim contract** (the prelude): an opaque `ext type JsRef` plus dynamic-access primitives — `js_get` / `js_call` and the value coercions (`js_str`/`js_num`/`js_bool` out, `js_of_*` in). Declared with the existing `ext` mechanism; the host provides the trivial implementations (on JS: `(o,k)=>o[k]`, `(o,m,...a)=>o[m](...a)`).
- **Object types → opaque-handle wrappers.** Every interface/class/object-type becomes `struct X { inner: JsRef }` plus an `impl` whose accessor methods delegate through the shim. The wrapper is a real nominal neoc type, so it works with the internals (methods, traits, `match`); the foreign object stays opaque inside.
- **Functions / consts → raw `#[link]` imports.** Free functions import via `extern "<host>" { #[link(name=…)] … }`; object/list/option positions reduce to the raw `JsRef` (wrap a result as `X { inner: … }`).
- **Ambient globals → accessors rooted at `js_global()`.** A global function becomes `fn f(…) { js_call(js_global(), "f", …) }`; a global var becomes a 0-arg accessor reading the root; global object types become wrappers. So `console`, `fetch`, the global `Bun` object are reachable without an import (the neoc#63 mechanism — see [Runtime](#runtime-the-host-shim)).

Primitives map 1:1 (`string`/`number`/`boolean → bool`, `void → ()`); anything that isn't a primitive or a known wrapper reduces to `JsRef`. All TS → neoc decisions live in [`src/generate.ts`](src/generate.ts).

### Scope

The CLI pulls in the **whole TypeScript world reachable from the configured packages** — not just each package's own files, but everything the compiler resolves while loading them: the standard library (`lib.es*`, `lib.dom`: `Math`, `JSON`, `Promise`, `Date`, `Map`, `Set`, …) and all transitive dependencies. The global surface comes from three sources, following TypeScript's own notion of "global":

- `declare global { … }` augmentation blocks (how `Bun` is bound);
- top-level ambient declarations of *global script* files — a `.d.ts` with no top-level `import`/`export`, where runtime globals like `console`, `fetch`, `setTimeout` live;
- top-level `declare namespace` objects (`Reflect`, `Intl`, `WebAssembly`).

`/// <reference types="x" />` entry shims (like `@types/bun`) are followed to the referenced package. The result is large — tens of thousands of lines for a runtime types package — by design: the package's complete type surface is available to neoc.

(The lower-level library functions `generate`/`generateModule`/`generateGlobals` harvest only the explicitly-loaded files, not the whole program; they take `--module <name>` filters and `--no-globals`. The convention-driven CLI does not.)

### v1 scope / next steps

- **Opaque-handle wrappers only.** Every object type is a `{ inner: JsRef }` wrapper with accessor methods. cxx's *by-value* mode — validate-and-copy a plain data record into a tagged `struct` so it's `match`-able — is the next step.
- **Raw imports are untyped at object positions** — free functions take/return `JsRef` for non-primitive args; a safe wrapped-function layer is future work.
- **Generics are preserved.** Type parameters emit on structs, impls, free functions, and methods (`pub struct Map<K, V>`, `pub fn map<U>(…) -> Box<U>`), and instantiations carry their arguments (`Promise<Response>`). A type parameter resolves to itself when in scope and degrades to `Unknown` otherwise; arrays become `[T]`, and `T | undefined` folds to `T`. Heterogeneous unions, tuples, `any`/`unknown`, and anonymous object types degrade to `Unknown` by design — the EXTERN.md degradation policy (neoc has no sum types; `Unknown` is the honest dynamic-boundary type).
- **The host must provide the shim** (`js_get`/`js_call`/coercions). Trivial on JS; neoc's JS runtime support is nascent — that's the one real dependency.
- **Names neoc can't spell** (e.g. Bun's `$`) aren't bound as identifiers, but remain reachable through the global root (`js_get(js_global(), …)`).

## Runtime (the host shim)

Generated headers declare the dynamic-access primitives as `ext`; the emitted neoc-JS calls them as ambient globals. autots ships their JavaScript implementation, so a host gets both halves:

```js
import { installShim } from "@neoc-sh/autots/runtime";
installShim();                              // js_global / js_get / js_call / coercions on globalThis
const { main } = await import("./your-compiled-neoc.js");
main();
```

**Ambient globals** (`console`, `fetch`, the global `Bun` object, even `globalThis.Bun.$`) are reached through the global root — `js_global()` returns `globalThis` (on Lua it would be `_G`). Per the resolution of [neoc#63](https://gitlab.beluga-sirius.ts.net/flying-dice/neoc/-/work_items/63), this is how the bindgen wraps globals and oddly-named exports — no neoc language change.

Proven end-to-end ([`packages/bun-http-sqlite/`](../bun-http-sqlite)): a neoc HTTP server reaches `Bun.serve` and `bun:sqlite` through the global root, compiled with `neoc build --target js` and run on Bun.

## Develop

Built with [Bun](https://bun.sh).

```sh
bun install
bun test                       # run the suite
bun run dev src/index.ts       # run the CLI against a file
bun run typecheck              # tsc --noEmit
bun run build                  # tsc -> dist/ (what npx ships)
```

The published `bin` (`dist/cli.js`) is plain Node-runnable JS, so `npx autots` works without Bun on the consumer's machine.
