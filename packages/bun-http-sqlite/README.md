# bun-http-sqlite

A neoc HTTP server backed by SQLite, reading natural-looking neoc that compiles to
plain JS — **no runtime shim, no `js_*` plumbing**. It composes both code generators:
**autots** (TS → neoc bindings) for the `bun:sqlite` handle and the Bun globals, and
**autosql** (SQL → neoc) for a typed query DAO.

- `GET /notes` — list all notes (via the DAO's `list_notes`)
- `GET /add/<text>` — insert a note (via the DAO's `add_note`)

## How it's wired

- **`src/sqlite.neoc`** — generated by [`autots`](../autots) from `@types/bun`'s
  `bun:sqlite` surface: `extern { #[extern(path = "bun:sqlite")] mod sqlite { … } }`
  describing `Database`/`Statement`/`Changes`. Regenerate with `bun run gen:ts`.
- **`src/notes.neoc`** — generated by `neoc autosql` from `sql/{schema,queries}.sql`:
  the `SqlValue` enum + `SqlExecutor` trait, a typed `Note` struct, and `list_notes` /
  `add_note`. Regenerate with `bun run gen:sql`.
- **`src/main.neoc`** — the app. It declares the `Bun` global and `Response` as
  `#[extern(ambient)]` (reached through the JS global root, no import), and implements the
  database seam the autosql DAO expects:
  ```neoc
  struct BunSqlite { db: Database }          // a neoc struct over the extern handle
  impl SqlExecutor for BunSqlite { … }       // the only code that touches the DB
  // handle: list_notes(db) / add_note(db, body) — typed Note results
  ```

`prebuild` regenerates both `.neoc` headers and concatenates `sqlite.neoc + notes.neoc +
main.neoc` into a single `src/app.neoc`, then `neoc build` compiles it to `dist/`.
(Concatenation is the current single-module workaround — splitting these into separate
`use`d files waits on multi-file support.)

## Run

```sh
bun run build    # gen:ts + gen:sql -> concat -> neoc build --target js
bun run start    # starts the server on http://localhost:38573
```

```sh
curl localhost:38573/notes          # 1:hello | 2:world |
curl localhost:38573/add/from-neoc  # added: from-neoc
curl localhost:38573/notes          # 1:hello | 2:world | 3:from-neoc |
```

The emitted JS is idiomatic — `new sqlite.Database(":memory:")`, `Bun.serve({ port, fetch })`,
`new Response(body)`, `db.query(sql).values()` — with `import * as sqlite from "bun:sqlite"`
the only import.

## Caveats (demo-grade `SqlExecutor`)

The hand-written executor is honest about two current limitations:

- **Params are inlined into the SQL**, not bound. autots's degradation drops the variadic
  bindings parameter from `bun:sqlite`'s methods, so there's no parameter slot to bind
  through; `bind()` substitutes literals instead. Fine for an in-memory demo, but it's
  string interpolation (no escaping). Native binding returns once variadic params lower as
  `[T]` (a deferred autots-fidelity item).
- **Result cells are typed by `value.constructor.name`** (`"Number"`→`Real`, `"String"`→
  `Text`). A genuine `NULL` cell would have no constructor; the demo's schema is `NOT NULL`.
