# App frames: key user journeys

An app can draw its own screens in the web framework its developer knows (Svelte, React, plain JavaScript), on a
backend written in Luau. Its window is a frame of the shell that loads the app's page, or the app opens alone at `/apps/<id>`; the client calls its
backend (`api`, typed from the app's one contract), hears what the backend sends (`host.on`), and reaches nothing else. The journeys use the two
framework fixtures, `tasks-svelte` and `tasks-react`: the same task list written once in each framework, Vite
projects on one OpenRPC contract (`e2e/apps`; they are built for the tests and are not in Discover). Every journey runs against both.

Automated twins have the same ids: `e2e/appframes.journeys.spec.ts` (the two apps share their data, so they run one
after another).

| Id  | Who / goal                                                                 | Starts at                          | Done when                                                                                                                                                                                 |
| --- | -------------------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AF1 | Install an app that has a client of its own and open it.                   | A host that does not have the app. | The app is in the Dock; opened, its window shows the app drawn by its client.                                                                                                             |
| AF2 | Add a task and see it in the list.                                         | The app open.                      | The task is listed and the field is empty; after a reload of the page the task is still there (it is the backend's data); it ticks off.                                                   |
| AF3 | Add a task with no title.                                                  | The app open.                      | A message from the backend says what is wrong; the window stays live, and the next add works and clears the message.                                                                      |
| AF4 | Let an agent add a task while the window is open.                          | The app open, an agent connected.  | The task appears in the open window with no reload and no click.                                                                                                                          |
| AF5 | Try to make the client reach out (network, the shell, storage).            | The app open.                      | Every attempt fails: no fetch, no socket, no access to the host page's DOM, cookie, storage or location, no popup, no form submission. |
| AF6 | Switch the shell between light and dark.                                   | The app open.                      | The app follows at once, without reloading; the app's styles did not change the shell.                                                                                                    |
| AF7 | Use two apps with clients side by side.                                    | Both apps open.                    | A task added in one is not in the other: each client reaches only its own backend.                                                                                                        |
| AF8 | A client sends its frame to another page (`location.href`).       | The app open.                      | The window notices it is not showing the page it loaded, says the app left its page, and "Try again" brings the app back. |
| AF9 | A client submits a form nobody prevented, and one by script with `form.submit()`. | The app open.            | The first stays on its page (a dialog form still closes its dialog); the second sends the frame away and the window says the app left its page, with Try again; no data is sent. |
| AF10 | An app's handlers never answer: use the shell and another app meanwhile, close and reopen the hung app's window. | An app with a handler that waits for ever. | The shell's own calls and the other app work throughout; the hung app's calls wait their turn (at most eight run at a time); closing the window ends the handlers the host was running, so the reopened app is whole. |
| AF11 | Uninstall an app while calls to its handlers are running. | An app with handlers that wait. | The calls are answered at once with the reason; the host keeps nothing running for them. |
| AF12 | Type something in an app's page, open another app, and come back. | Each fixture, opened with the other available in the Dock. | The window is hidden, not gone, while the other app is in front; coming back shows the same document with what was typed in it still there, and the app still works. |
| AF13 | Send the backend a call its definition does not allow.         | The app open.                      | The router refuses it with a JSON-RPC error that says what is wrong (invalid params, method not found); the window is unharmed.           |
| AF14 | Check what the app's page is allowed to load and ask for.                  | The app open.                      | The page's policy has `sandbox` and no network; an origin the app declared in `x-app` is in it and none else; a permission it declared is allowed in the frame and one it did not is not. |
| AS1 | Open the app on its own page, `/apps/<id>`, with no shell.                 | A paired device.                   | The page is the app and nothing else (one frame, no Dock); it works, says it runs on its own, and shows the same data as its window.                                                      |
| AS2 | On its own page, let an agent change the data; switch the browser to dark. | The app open on its own.           | The task appears with no reload; the app follows the browser's appearance live, without reloading.                                                                                        |
| AS3 | On its own page, try to make the client reach out.                         | The app open on its own.           | Every attempt fails, as in the shell.                                                                                                                                                     |
| AS4 | Open an app's own page from a device that is not paired.                   | An unpaired browser.               | A plain page says to pair first, with a link to the shell; no app is shown.                                                                                                               |
| AS5 | Open an app's static address directly in a tab.                            | A paired device.                   | The page is as contained as in the frame (an opaque origin) and says it needs its host page rather than hang.                                                                             |
| AF15 | A page's script throws while it loads.                                  | An app whose page throws.          | The window shows the script's own message with Try again (the script is loaded from the host as a module, so the browser reports what went wrong). |
